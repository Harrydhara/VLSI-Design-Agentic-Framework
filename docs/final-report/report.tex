\answerbox{\textbf{Abstract.} We built an agent that writes Verilog RTL and a self-checking testbench from a
specification using a local language model (\fact{model}), checks both with Icarus Verilog and Yosys, and revises
from the tool feedback for up to \fact{max-attempts} attempts, together with a browser dashboard and a container
image that make it usable in a course. Hidden reference tests that the agent never sees score every attempt, so
each run yields a paired one-shot and iterative result. Over \fact{runs} runs on \fact{circuits} circuits with four
prompt strategies, revising fixed \fact{fixed} one-shot failures and broke \fact{broken} correct designs; most fixes
were compile errors that the tools named by line, and no revision fixed a specification-level logic bug unless the
testbench was written separately from the design. The bottleneck is the model's own testbench: on circuits held out
during development it rejected \fact{heldout-rejected-range} of the designs that were in fact correct, so most
revisions went into designs that were already right.}

\section{Introduction}

Large language models can write Verilog that looks right and compiles, yet describes the wrong circuit. That gap is
the point of departure of our proposal: a student should be able to watch an agent generate a design, see a test
fail, inspect the revision, and learn which settings actually make the hardware correct. Tool feedback seems the
obvious remedy. A compiler names the line it rejects and a testbench names the input it fails, so an agent that
feeds these messages back to the model should improve on its first attempt.

We test that claim directly. Our agent generates a design and a testbench from a specification, runs development
checks (compilation, simulation of its own testbench, synthesis), and revises from their results. A separate
reference test, written by the team and never shown to the agent, decides whether a design is correct. We ask two
questions: \emph{does iterating on tool feedback beat one-shot generation}, and \emph{how reliable is the feedback
that the agent gives itself}?

This report describes:
\begin{itemize}
  \item the agent, with a single-conversation workflow and a workflow that writes the testbench from the
        specification before any design exists (Section~\ref{sec:design});
  \item an evaluation that keeps the agent away from the tests that score it, scores every attempt so that one run
        gives paired one-shot and iterative results, and uses a held-out set of circuits declared in advance
        (Sections~\ref{sec:design} and~\ref{sec:method});
  \item the toolkit students use: a dashboard to run the agent, inspect every attempt down to waveforms, edit and
        re-test its RTL, compare strategies and write new ones, delivered as a tested, published container image
        (Section~\ref{sec:toolkit});
  \item the results of \fact{runs} benchmark runs and what they say about where agentic RTL generation fails
        (Sections~\ref{sec:results} and~\ref{sec:discussion}).
\end{itemize}

\section{Related work}\label{sec:related}

% Every claim below was checked against the cited paper itself; docs/final-report/citations.md says where.
\textbf{Benchmarks.} Thakur et al.~\cite{thakur2023} fine-tuned open code models on Verilog collected from GitHub and
textbooks and tested them with testbenches on 17 problems of graded difficulty; the fine-tuned CodeGen-16B outperformed
the commercial Codex model on functional correctness. VerilogEval~\cite{verilogeval} turned 156 problems from the
HDLBits exercise site into text-only descriptions, one set written by hand and one generated with GPT-3.5, and scores
a completion by simulating it with Icarus Verilog against a golden solution, reporting pass@$k$. Its
revision~\cite{revisiting} adds specification-to-RTL tasks and classifies failures automatically.
RTLLM~\cite{rtllm} provides 30 designs, each with a description, a testbench and a hand-written reference design, and
grades three goals in turn: syntax, functionality, and design quality as power, performance and area after synthesis.
In all of them the test that decides correctness is written by the benchmark's authors, never by the model under
test. Our hidden reference tests follow the same rule.

\textbf{Loops with feedback.} In Chip-Chat~\cite{chipchat} an experienced engineer worked with ChatGPT-4 to design an
8-bit accumulator-based processor that went to tapeout on a SkyWater 130\,nm shuttle; the engineer steered the
conversation and verified the output, writing the testbenches. AutoChip~\cite{autochip} replaced the engineer with
tools: each candidate is compiled with Icarus Verilog and simulated with a testbench supplied with the problem, and
the errors and mismatches go back to the model until every test passes or an iteration limit is reached. With
feedback from only the latest iteration it produced 24.2\% more functionally correct code than zero-shot generation.
RTLFixer~\cite{rtlfixer} found about 55\% of the errors in LLM-written Verilog to be syntax errors and, with
retrieval-augmented generation and ReAct prompting, fixed about 98.5\% of the compilation errors in its dataset.
Multi-agent systems go further. VerilogCoder~\cite{verilogcoder} plans a module as a dependency graph of sub-tasks
and gives its debug agent a simulator and a waveform tracer that follows a mismatched signal back through the
abstract syntax tree. MAGE~\cite{mage} samples many candidate designs at high temperature, scores them in simulation,
and debugs them with checkpoints of the expected internal state that locate the first mismatch. With GPT-4 Turbo and
Claude~3.5 Sonnet respectively, they report 94.2\% and 95.7\% on the revised VerilogEval~\cite{revisiting}.

\textbf{Who writes the test.} These loops differ in where the test that drives them comes from, and that is the
question our study isolates. In AutoChip the testbench that produces the feedback is also the one that decides
success, and VerilogCoder's debug agent revises until the code passes a provided testbench. MAGE has an agent write
the testbench from the specification, combined with the golden testbench when one is available, and a judge agent
that regenerates the testbench when it decides that the testbench, not the design, is wrong. Writing the test is
itself hard: in AutoChip's evaluation the problems that asked for a testbench fared worst, with none of the generated
code compiling, and AutoBench~\cite{autobench}, an LLM testbench generator, reports that generating testbenches
directly has a low pass rate. AutoBench counts a generated testbench as preliminarily correct only if it reports no
errors on the golden design, the same false-rejection measure we apply to our agent's testbenches
(Section~\ref{sec:own-checks}).

\textbf{Self-correction.} Self-Refine~\cite{selfrefine} has one model write, critique and revise its own output, and
reports an average gain of about 20\% absolute over one-step generation across seven tasks. Huang
et al.~\cite{huang2024} find that without external feedback, models struggle to correct their own reasoning and
sometimes get worse. Our agent sits between the two: the compiler and the synthesizer give external feedback, but
the testbench that judges behavior is the model's own, so the feedback on function is only as good as the model's
reading of the specification.

\textbf{Adapted models.} Another line of work changes the model rather than the loop. RTLCoder~\cite{rtlcoder}
fine-tunes a 7B model on more than 27,000 instruction--code pairs generated with GPT-3.5 and outperforms GPT-3.5 on
RTL benchmarks, arguing that a local open model removes the privacy concern of uploading every instruction to a
commercial provider. ChipNeMo~\cite{chipnemo} adapts LLaMA2 models to chip design through domain-adaptive
tokenization, continued pretraining, alignment and a domain-adapted retrieval model, and evaluates them as an
engineering assistant chatbot, for EDA script generation and for bug summarization. We used an unmodified model
through Ollama, so our results describe an off-the-shelf model inside the loop; fine-tuning was a stretch goal we did
not attempt (Section~\ref{sec:conclusion}).

\textbf{What this study adds.} We do not propose a stronger generator: our circuits are smaller than these
benchmarks' and our model (\fact{model}) runs locally. What we add is measurement. First, the agent never sees the
test that scores it, and every attempt is scored, so each run yields a paired one-shot and final result and counts
both the failures that revision fixed and the correct designs it broke. Second, we measure the agent's own checks
against that independent test, which shows how often a model-written testbench rejects a correct design: the
quantity that decides whether a loop like AutoChip's can work where no reference testbench exists. Third, the
held-out circuits and runs were declared before each round, and strategies were tuned on the dev circuits only.

Figure~\ref{fig:loop} shows the loop. The model receives the circuit's description and its exact module header and
replies with two Verilog blocks: the design and a self-checking testbench that must end by printing
\texttt{RESULT: passed/total passed}. The framework extracts the code, compiles design and testbench with Icarus
Verilog, runs the testbench, and synthesizes the design with Yosys, flagging inferred latches. If any of these
development checks fails, their output (capped at a few thousand characters) goes back to the model with a request
to fix the design or, if a check itself is wrong, the testbench. The run stops when the checks pass, after
\fact{max-attempts} attempts, or when its budget of \fact{budget} tokens is spent. Every tool runs with a timeout and
capped output, so a design that hangs the simulator ends as a timeout instead of stopping the agent.

The second workflow, \texttt{spec\_first}, splits the work into two conversations. One writes the testbench from the
specification alone, before any design exists, and must show that it runs against a placeholder design. The other
writes the design and never sees the testbench. When a design fails some of the testbench's checks, the failing
checks first go back to the testbench's author, who either corrects its testbench or confirms it; only then does
the design conversation get the feedback.

Every run writes an event log as it happens and a history file at the end with the settings, every model call,
every attempt's checks and scores, and a copy of the prompts the run used, so that results stay interpretable after
a strategy is edited.

\subsection{Keeping the evaluation honest}

The agent is scored only by the hidden reference tests. They are written by the team, kept outside everything the
model sees, and run only after the loop has finished. A generated design could in principle print a fake result
line and stop the simulation; to rule that out, each run replaces a placeholder in the reference test's result line
with a fresh random token, and only a line carrying that token counts. The reference tests are exhaustive for the
combinational circuits and combine directed and random sequences for the sequential ones.

Because every attempt is scored, attempt~1 is exactly what a one-shot run would have produced, and the final
attempt is the iterative result. Each run therefore gives a paired comparison, and shows when a revision fixed a
failing design or broke a correct one.

The reference tests are themselves tested. Each circuit comes with hand-written correct and deliberately faulty
designs (\fact{fixtures} in all, \fact{fixtures-correct} of them correct). Every correct design must pass, and every
faulty one must fail for its intended reason: a dropped carry, a reset of the wrong kind, swapped multiplexer
selects, a signed comparison done unsigned, a simulation that never finishes. The acceptance checks in
\texttt{docs/acceptance-checks.md} record this together with each team member's completion check.

\section{The toolkit}\label{sec:toolkit}

The dashboard is a browser application (Gradio and Plotly) organized in five sections. A student picks a circuit,
whose specification and module header are shown, a strategy, one-shot or iterative mode, the attempt limit and the
model, and watches the run's log stream in as it happens (Figure~\ref{fig:run-log.jpg}). A scripted model replays a
recorded adder4 run, so the interface can be tried without a GPU.

\screenshot{run-log.jpg}{0.72}{A run of the agent on alu4: the dashboard's status line and live log. The model's own
testbench fails every attempt (13/15 checks), so the agent revises twice and stops at the limit, while the hidden
test passes all three designs.}

The results section opens any saved run, whether started from the dashboard, the command line or a benchmark, and
shows for each attempt the agent's checks next to the hidden test's verdict, the design and testbench, the changes
from the previous attempt, the hidden test's mismatch lines, the feedback the model received, and the model's raw
reply. A waveform view re-runs the hidden test on any attempt and plots the circuit's inputs and outputs, with the
test's expected values beneath them, around the first mismatch (Figure~\ref{fig:waveform.jpg}).

\screenshot{waveform.jpg}{0.72}{The waveform view on a held-out alu8 design with a signed-comparison bug. For the
operation SLT (op 7) the design keeps \texttt{y = 1} while the expected value drops to 0 once \texttt{b} becomes
negative; dashed lines mark the reported mismatches.}

Students can also edit an attempt's design or testbench and run exactly the checks the agent's attempts get. The
edited code goes through the same loop as a single attempt, and the result is saved as a new run that records where
it came from (Figure~\ref{fig:edit-retest.jpg}). The remaining sections chart any benchmark
(Figure~\ref{fig:benchmark-charts.jpg}) and provide a strategy editor, which copies a strategy, checks its template
placeholders, previews the prompts as the model will receive them, and saves the copy without touching the shipped
strategies. Runs and benchmark results can be exported as archives and standalone pages.

\screenshot{edit-retest.jpg}{0.62}{Editing and re-testing the design of Figure~\ref{fig:waveform.jpg}. Declaring the two
sign-extended operands \texttt{signed} makes the hidden test pass all 524,288 checks, while the model's own testbench
still reports 0/22.}

\screenshot{benchmark-charts.jpg}{0.95}{Two of the dashboard's five benchmark charts for the held-out circuits:
passes after each attempt, and passes per circuit (one-shot $\to$ iterative). The dashboard names strategies by
folder, so \texttt{spec\_first} there is version~2.}

For delivery, the toolkit ships as a container image with the exact tool versions the benchmarks used: Icarus
Verilog~12, Yosys built from the same commit, and pinned Python packages. A Compose file starts the dashboard
together with an Ollama server on the GPU and downloads the model on first start; runs and custom strategies are
kept in the project folder across container restarts. A continuous-integration workflow builds the image on every
push to the main branch, runs the fixture check and the test suite inside it, and only then publishes it, so a
teammate can pull a tested image instead of building one. Following Member~3's completion check, a fresh clone with the published
image was used to open the dashboard, run an example, edit and rerun a strategy, and export the result, and the
runs and strategy survived recreating the container.

\section{Experimental method}\label{sec:method}

All runs used \fact{model} through Ollama on one RTX 4090, at temperature \fact{temperature} with thinking disabled,
at most 4,096 output tokens per reply, and up to \fact{max-attempts} attempts and \fact{budget} tokens per run (no
run reached the budget). Each strategy ran every circuit with seeds \fact{seeds}. With the same seed and prompt a run
repeats exactly, so each seed is one independent sample.

We compared four strategies:
\begin{itemize}
  \item \texttt{default}: the starter prompts, kept unchanged as the baseline;
  \item \texttt{tb\_timing}: the same, plus advice on when a testbench should sample a clocked output;
  \item \texttt{spec\_first} v1: the two-conversation workflow of Section~\ref{sec:design};
  \item \texttt{spec\_first} v2: the same, but the testbench's author must quote the sentence of the specification
        behind any expected value it changes.
\end{itemize}

We report, as the proposal promised, compilation, hidden-test pass rate, synthesis, attempts used, time and tokens,
and cell counts only for designs that pass the hidden test, all synthesized with the same generic Yosys flow. The
work proceeded in a fixed order: a difficulty check with one-shot runs on the four harder circuits (seeds 101--105),
then strategies were developed and compared on the dev circuits only, declared in a commit, and run once on the
held-out circuits without further tuning. Round~1 compared \texttt{default} and \texttt{tb\_timing}; round~2 added
both versions of \texttt{spec\_first}.

\subsection{How reliable were the agent's own checks?}\label{sec:own-checks}

Every attempt that produced code was judged twice: by the agent's development checks and by the hidden test.
Figure~\ref{fig:own-checks} and Table~\ref{tab:own-checks} compare the two. On the held-out circuits every strategy's

\section{Discussion}\label{sec:discussion}

\textbf{What iteration fixes.} The revisions that turned failures into passes were mostly compile errors that the
tools reported by line. In both held-out mux4 fixes the design assigned the output inside an \texttt{always} block
but declared it as a plain output; Icarus Verilog reported \texttt{y is not a valid l-value}, and the model changed
one declaration. Most of \texttt{spec\_first}'s held-out recoveries on seqdet\_mealy were the same kind of error.

\textbf{What it does not fix.} No revision in round~1 fixed a specification-level logic bug. The dominant one was the
ALUs' set-less-than: the specification asks for a signed comparison, and the model sign-extended both operands and
compared them with \texttt{<}, which remains unsigned (Appendix~\ref{app:example}). The feedback could not help,
because it came from the model's own testbench, and that testbench was wrong in other ways.

\textbf{Why: the checks are the bottleneck.} The proposal named as its biggest risk that the model would write a
design and a testbench with the same mistake. That happened, but the larger problem was broader: the model's
testbenches sampled clocked outputs at the wrong moment, computed wrong expected values, failed to compile, or never
printed a result. A loop is only as good as its checks, and here the checks rejected most correct designs, so most
revisions were spent on designs that were already right, and occasionally broke them.

\textbf{Separating the testbench's author helps only partly.} Writing the testbench first, in its own conversation,
lowered false rejections on the dev circuits from 51\% to 21\% and was the only strategy whose revisions fixed the
signed-comparison bug (3 dev runs). On the held-out circuits the gain did not hold: false rejections stayed at
\fact{heldout-sfone-rejected} and \fact{heldout-sftwo-rejected}, and the strategy ended at
\fact{heldout-sfone-final} and \fact{heldout-sftwo-final} against \fact{heldout-default-final} and
\fact{heldout-tbtiming-final} for the simpler strategies, at the highest token cost. Requiring the author to quote
the specification stopped it from giving in to buggy designs, but it then defended testbenches whose expected values
were right and whose timing was wrong.

For a teaching toolkit this points to where effort pays off: better checks (for example a testbench harness that
fixes when outputs are sampled) rather than more elaborate revision prompts. The dashboard's edit-and-re-test view
makes the point tangible: a one-word fix passes the hidden test while the model's own testbench still fails it.

\section{Limitations and threats to validity}

\begin{itemize}
  \item \textbf{Small samples.} Each strategy has 25 runs per split; differences of one to three runs are within noise.
  \item \textbf{One dominant bug.} Most logic failures were the ALUs' signed comparison, so conclusions about which
        logic bugs iteration can fix rest mostly on one bug type.
  \item \textbf{One model and setting.} All runs used \fact{model} at temperature \fact{temperature}; other models or
        settings may revise differently.
  \item \textbf{Small circuits.} At most 8 bits and a handful of states.
  \item \textbf{Strategies change the first prompt too.} \texttt{tb\_timing}'s and \texttt{spec\_first}'s one-shot
        results differ from \texttt{default}'s partly because their prompts differ, so the comparison is not a pure test
        of feedback.
  \item \textbf{Bounded evidence.} Passing a reference test is strong evidence, not proof; the reference tests were
        written by the team and checked with fixtures. Cell counts are not power, area or timing.
  \item \textbf{Held-out circuits used more than once.} They served in the difficulty check and in both rounds, though
        strategies were tuned on dev only and each round's held-out runs were declared beforehand.
  \item \textbf{Stretch goals not attempted.} Retrieval-augmented generation and LoRA fine-tuning were left out.
\end{itemize}

\section{Conclusion and future work}\label{sec:conclusion}

Iterating on tool feedback improved one-shot generation only slightly: it reliably repaired errors the tools could
name, but rarely the logic, because the model's own tests rejected most correct designs and missed or shared the
real bugs. Making an agent better at hardware therefore starts with making its checks trustworthy.

Next steps follow from that: a testbench harness that provides the clock, reset and sampling time, so the model
writes only stimulus and expected values; keeping the last design that compiled and stopping when a revision repeats
the previous design; retrieval of verified Verilog examples and fine-tuning with separate training and evaluation
data, the stretch goals left open; a review agent that judges disputed checks; and larger circuits such as a FIFO,
more seeds and a second model.

\section{A worked example: the signed-comparison bug}\label{app:example}

Run \texttt{runs/bench/heldout-seeds1-5/runs/alu8/default/seed4}. The specification defines operation 111:

\begin{code}
111  SLT   1 if a < b as signed two's complement numbers, otherwise 0
\end{code}

All three attempts implemented it the same way:

\begin{code}
wire [8:0] sa = {a[7], a};
wire [8:0] sb = {b[7], b};
...
3'b111: begin // SLT
    y_reg = (sa < sb) ? 8'h01 : 8'h00;
end
\end{code}

Sign extension does not make \texttt{<} signed: both vectors are still unsigned, so $b = -128$ becomes
\texttt{9'h180} and compares as larger than 0. The model's own testbench could not reveal this. It failed every one
of its checks with all outputs unknown. This is how the feedback after attempt~1 began (after attempt~2 it was the
same with 0/22):

\begin{code}
- The testbench reported failures (0/23 checks passed):
FAIL: a=170 b= 85 op=000 | Expected: y=  0 z=1 c=0 v=0 n=0 | Actual: y=  x z=x c=x v=x n=x
FAIL: a=255 b= 15 op=000 | Expected: y= 15 z=0 c=0 v=0 n=0 | Actual: y=  x z=x c=x v=x n=x
...
\end{code}

The hidden test scored all three attempts 491,520 of 524,288 and pinpointed the operation:

\begin{code}
MISMATCH op=111 a=0 b=128: expected y=0 zero=1 carry=0 overflow=0 negative=0, got y=1 zero=0 ...
\end{code}

Figure~\ref{fig:waveform.jpg} shows the same failure as a waveform. Editing the design in the dashboard to declare
\texttt{wire signed [8:0] sa} and \texttt{sb} makes the hidden test pass all 524,288 checks, while the model's
testbench still reports 0/22 (Figure~\ref{fig:edit-retest.jpg}; the run is saved in \texttt{runs/manual/}).
